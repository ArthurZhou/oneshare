# 权限模型（ACL）

OneShare 采用 **ACL（访问控制列表）**：按**路径**配置规则，规则可绑定到**用户**或**分组**，从而决定谁能读取/写入哪些目录。

---

## 权限级别

| 权限 | 能力 |
|------|------|
| `read`（读） | 列出目录、下载文件 |
| `write`（写） | 上传、新建文件夹、重命名、移动、删除（隐含读） |
| `admin`（管理） | 完全控制（当前实现为：管理员用户绕过所有 ACL） |

> 权限是**单向覆盖**的：`write` 包含 `read`，`admin` 包含全部。

---

## 核心规则

1. **路径前缀匹配**：对 `/photos` 的规则适用于 `/photos` 及其所有子目录（精确匹配或子路径，绝不匹配同前缀的“兄弟”，如 `/photos-secret`）。
2. **默认拒绝（fail-closed）**：任何路径只要没有可匹配的 ACL 规则，就**谁都不能访问**。ACL 只负责授权，不会“默认可读”。
3. **最具体优先**：同一条路径有多条可匹配规则时，路径最长（最具体）的规则生效；其中第一条匹配到该用户/分组的子规则决定权限。
4. **管理员绕过**：`is_admin` 用户不受 ACL 限制，可见并操作整个 `root_dir`。

---

## 规则的目标

每条 ACL 规则绑定到：
- **一个用户**（user-level），或
- **一个分组**（group-level）

两者在同一规则中互斥（要么 user_id 要么 group_id）。

---

## 保留分组

### `default`（默认组）

- 任何**没有被分配到显式分组**的已登录用户，都被视为 `default` 组成员。
- 用途：用一条 ACL（如 `/public → default（读）`）给所有“未分组用户”一个基础访问范围。
- 注意：被分配到显式分组的用户**只使用**这些分组，**不会**再继承 `default`。
- 不可删除。

### `guest`（访客组）

- 任何**未登录**的访问者都被视为 `guest` 组成员。
- 用途：用一条 ACL（如 `/public → guest（读）`）把某个文件夹设为**公开可读**（无需登录）。
- 访客永远不是管理员，也永远看不到管理界面；未登录访问者直接浏览 `guest` 授予的内容，页头保留登录链接。
- 不可删除。

> 常见组合：`/public → guest（读）` + `/public → default（读）` + `/public → 某分组（写）`，即可做到“公开可读、登录可读、特定成员可写”。注意同一路径尽量只配一条规则并取其最高权限（见下）。

**踩坑提示**：`can_access` 对同一路径取**第一条**匹配的用户/分组子规则；若同路径同时存在 read 与 write 两条规则，先命中的 read 会“赢”，write 反而被拒绝。请为同一路径只保留一条取最高权限的规则。

## Samba 风格的虚拟根目录

对**非管理员**用户，网页根目录 `/` 是一个**虚拟共享根目录**：

- 用户可读的每个配置了 ACL 的目录，都会以顶层文件夹出现，文件夹名 = 该目录的**叶子名称**。
- 共享层级以上的部分被隐藏：对 `/nested/public2` 配了 ACL，用户看到的是顶层 `public2`，路径始终显示为 `public2/…`，看不到 `/nested`。
- 叶子重名自动消歧：`data`、`data-2`、`data-3`…
- 地址栏反映虚拟路径：`#/public2/sub`。

**管理员不受虚拟根目录影响**：他们浏览的是真实文件系统树，能看到真实路径 —— 这正是配置 ACL 所需的。

---

## 真实路径保护

对非管理员用户，**真实文件系统路径永远不会发送到前端**：

- 列表接口只返回虚拟/显示路径；
- 文件传输使用不透明的 `v1.…` shadow（AES-256-GCM 加密的路径密文）；
- 服务器内部把虚拟路径解析为真实路径，并始终基于**真实路径**做 ACL 校验；
- 路径穿越（`..`、`\`）在到达 ACL 引擎之前就被 `resolve_virtual` / `sanitize_path` 拒绝，防止低权限用户借共享目录越权访问兄弟路径。

---

## 第一个用户 = 管理员

**第一个成功登录的用户会自动成为管理员**，之后可到「管理」面板配置 ACL、分组与用户。

---

## 角色 → 分组自动加入

若 OIDC Provider 的 `userinfo` 返回的 `role` 声明与某个**已有分组名**完全一致，该用户登录时会自动加入该分组（仅加入，绝不移除）。适用于企业场景：管理员预先按角色建好分组，用户登录即自动获得对应权限。
